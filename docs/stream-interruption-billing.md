## 为什么中断会导致输出为零

Anthropic 的 `message_start.message.usage` 通常提供输入和缓存消耗；输出累计计量通常随末尾 `message_delta.usage.output_tokens` 到达。文本、思考和工具参数可以在两者之间持续输出。若上游到网关的连接在最终 usage 到达前关闭，服务虽收到输出内容，却没有最终输出 token 数。

0.2.17 已经具备客户端断开后继续读取上游、错误时返回部分 usage，以及 handler 对部分结果计费的逻辑。因此只做“遇到错误也 RecordUsage”不能解决本次输出漏计问题。现场已验证输入和缓存正常计费，缺口是没有最终输出计量时的处理。

代码还忽略了 `message_start` 中可存在的 `output_tokens`。修复应先保存这部分上游实报计量；后续累计 usage 应覆盖它，而不是相加。

本地 token 费用按输入、输出、缓存创建和缓存读取各自的单价计算，再应用已有分组/用户倍率及长上下文、Fast 等规则。输出为零时，缺少的是 `输出 token × 输出单价` 对应的费用，并不意味着输入/缓存也应重新计费。对账时先对齐 token 分桶，再核对价格和倍率；本地 `actual_cost` 与供应商金额不一定采用相同价目表，不能仅凭两个金额不同就认定漏扣。

## 修复原则

1. 保留已有客户端断开排水逻辑，优先拿到上游最终 usage；客户端是否还在线不应决定是否计费。
2. 保存所有已观测的上游 token，包括起始事件的输出计量；错误不清零，累计值不叠加。
3. 上游最终 usage 缺失时，区分“确定为零”和“未知”，不能用零冒充完整的上游账单。
4. 如启用本地估算补计，应只统计实际收到的文本、思考和工具参数内容，避开 SSE 包装、签名、keepalive；同一内容不能因分片而重复收费。上游最终计量优先，本地估算必须可审计并明确标记来源。
5. 本地估算不能保证精确等于上游：服务端未送达的输出、不可见思考和私有 tokenizer 都可能造成差异。严格一致需要上游逐请求账单或查询接口，并以稳定的上游 request ID 幂等对账。

## 历史对账与上线边界

不依据耗时、max_tokens 或平均请求费用直接批量补扣历史账单。先导出候选请求并匹配上游请求 ID、用户、模型和时间；取得上游权威计量后，按已收费金额计算差额，保留对账记录，确保重跑不重复扣款。

部署前需要备份数据库、确认配置和迁移兼容性，再用可控上游模拟正常结束、客户端断开、EOF、RST 和超时。线上重启与历史补扣不属于本次只读调查，代码完成后应单独安排上线。

## 本次代码实现

修复作用于本次故障涉及的 Anthropic `/v1/messages` API Key 透传，以及同服务的普通 Anthropic SSE 转发路径。OpenAI、Gemini 等其他协议不套用 Anthropic 的计量估算规则。

- `message_start` 中的 `output_tokens` 不再丢失；后续累计计量覆盖旧值，显式输出零也被尊重。
- 默认启用 `gateway.stream_output_token_estimation`：只有缺少覆盖最新内容的上游输出计量时，才用 `cl100k_base` 对已收到的文本、thinking、工具参数做本地估算。用户已于 2026-10-18 明确同意估算补计并标记来源；中断结果中的估算输出通过原有 `RecordUsage` 路径计价、扣费、更新用量，仍可显式关闭。
- 整段拼接后计数，不按 SSE 分片数量收费；不计事件封装、ping、签名和工具参数占位空对象。不估算输入/缓存，避免猜测缓存命中率和重复收费。
- 估算值不低于已收到的上游输出计量。后续实报值存在时优先使用实报值，包括 0；正常结束且 usage 完整的请求不受估算影响。
- 单请求最多暂存 1 MiB 输出，防止无限占用内存；超过时只估算已保存前缀并在审计日志标记 `truncated=true`，不能据此声称计量完整。不可见思考、未到达代理的输出同样不能恢复。
- 新增 `usage_logs.output_tokens_estimated`，通过迁移 246 添加、默认 false，并同步 Ent schema/生成代码和手写 SQL 的单条、批量写入及读取。API 暴露同名字段；用户/管理员共用的用量表显示“估算”，导出包含来源标记。历史 false 只表示未采用本地估算，不代表其 usage 完整。
- 记录结构化 `anthropic_stream_output_estimated` 日志，含计费请求 ID、上游初始输出计量、估算值、长度及截断状态，不记录响应文本或提示词。此日志表示采用了估算；实际扣费仍以账单/账务记录为准。
- 对中断、客户端断开或采用估算的流式请求，计费任务使用已有 mandatory 提交路径：队列满且普通策略为 drop/sample 时同步兜底，避免已计算的费用再因队列丢弃而漏账。正常成功请求保留原队列策略。该保护不依赖估算开关；它不能替代数据库故障时的持久化重试或对账，也没有证据表明现场 8 条数据库取消错误由队列溢出引起。

估算补计默认开启；也可在现有配置的 `gateway` 节点内显式配置（不要重复创建同名节点）：

```yaml
gateway:
  stream_output_token_estimation: true
  stream_data_interval_timeout: 180
```

开关对应环境变量 `GATEWAY_STREAM_OUTPUT_TOKEN_ESTIMATION`，环境变量优先于配置文件。未配置时默认 true；显式设置为 false 可关闭。关闭时继续按已观测的上游 usage 收费，无法补回未收到的输出计量；开启时也不能承诺金额与上游完全相同，因为 Anthropic tokenizer 非公开，而且本地看不到上游未送达的输出。

如需精确对账，先核实上游实际使用的响应头名，再在账号设置中配置 `upstream_request_id_header`（例如确认后使用 `x-request-id`，不能凭空猜测）。随后要求供应商提供按该 ID 查询最终 input/output/cache usage 的能力。补差应具备唯一对账键、原始账单/原收费/差额记录、退款路径，并保持原始价格与倍率快照，不能直接用当前价格再次全额 RecordUsage。

## 验收场景

| 场景 | 期望 |
| --- | --- |
| 正常完成，末尾 usage 存在 | 完全按上游累计值；估算标记 false |
| 客户端断开，上游仍正常完成 | 继续读取最终 usage，正常收费 |
| 上游 EOF/RST/超时且已有输出，缺末尾 usage | 开启开关后补计已收到的输出估算，保留输入/缓存计量，估算标记 true |
| 仅收到 message_start 后断开 | 保存初始实报输出；不凭空生成输出估算 |
| 仅 ping/错误，无输出且无 usage | 不凭空扣 token 费 |
| 最终上游明确报告 output_tokens=0 | 不以本地估算覆盖零 |
| 相同内容以不同 SSE 分片到达 | 本地估算一致 |
| 请求 context 已取消 | usage 记录沿用独立计费 context |
| 用量队列满且普通任务配置为丢弃 | 中断/断开/估算的流式计费任务同步兜底，执行一次；普通成功请求沿用队列策略 |
| 重试、重复账单写入 | 沿用既有计费幂等键，不引入第二次追加扣费 |

上述行为需要部署修复代码、完成迁移并启用所选策略后才对新请求生效。8765 实例已于 2026-10-18 完成部署和迁移；历史账单未补扣。正常请求账单已验证写入，未在生产上人为制造断流来验证估算分支。

回滚时可先将开关改回 false，停止新请求的估算补计。迁移新增列应保留，以保存已产生账单的来源标记；不要删除估算账单、重置余额或重复提交原请求来“补账”。
